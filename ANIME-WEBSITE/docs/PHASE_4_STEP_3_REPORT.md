# Step 3 — Local load and security verification

Date: 2026-11-24. Product baseline: `2bedf5a`. No production behavior or rate policy changed in this step.

## Security verification

- Full offline suite: 28/28 passed after adding a security subtest. The final API test update independently passed 1/1.
- Real PostgreSQL account HTTP suite: 7/7 passed in an isolated temporary schema.
- New checks reject cross-site mutations even with a valid token, another account's CSRF token, duplicate session cookies, incorrect current passwords, malformed JSON and bodies over 8 KiB. Error responses omit stack details; CSP/nosniff and hidden framework headers were checked.
- Existing checks cover cookie attributes, authentication rate limits, session rotation/revocation, user-scoped favorites and signed cursors, secret-free export, explicit deletion confirmation and fresh reauthentication. Lifecycle checks cover expired sessions and seven-day inactivity.
- Code review: SQL values are parameterized; session tokens are stored hashed; CSRF uses HMAC and constant-time comparison; external query endpoints are allowlisted with redirects rejected and bounded response sizes. Frontend text is rendered through textContent/text nodes. These observations are scoped review evidence, not a penetration-test certification.
- `npm audit --omit=dev --json` reported zero known vulnerabilities (including zero High/Critical). Raw output: [DEPENDENCY_AUDIT_STEP_3.json](DEPENDENCY_AUDIT_STEP_3.json). This only reflects the advisory database at execution time and production dependencies.

## Load method

`backend/scripts/check-local-load.js` creates a random `load_*` PostgreSQL schema, migrates it and seeds 25 disposable users/sessions. It uses the real Express app on an ephemeral loopback port, a five-connection pool, and deletes only that schema on exit. It blocks outbound requests. No Wikidata traffic or persistent personal account data is used. Request and server processes share one machine; measurements are not Japan-region or production network results.

Profiles: 25 simultaneous authenticated reads; 5 requests/second for 60 seconds; 10 requests/second for 60 seconds; 25 simultaneous provider-free favorite deletions; 25 simultaneous login attempts. Timed profiles split requests evenly between health and authenticated reads. Each profile uses a fresh limiter instance, with all clients sharing one IP. Tokens for seeded sessions are generated by the harness and never saved to evidence.

Raw metrics: [LOCAL_LOAD_RESULTS.json](LOCAL_LOAD_RESULTS.json). Successful-response p95 excludes rejected requests; HTTP 429 is reported separately and never counted as successful capacity.

| --- | --- | --- | --- |
| 25 concurrent authenticated reads | 25/25 | 0 | 204.00 ms |
| 5 RPS profile: health | 150/150 | 0 | 3.68 ms |

Total: 1,000 requests, 775 successful and 225 rate-limited, no HTTP 5xx or transport errors. Favorite deletions are idempotent deletes of absent favorites (authenticated SQL write path), not a populated write workload. Login verifies real Argon2id hashes, with ten concurrent accepted attempts; it **exceeds the 500 ms target**. The timed profiles schedule requests across 60 seconds; they do not keep 25 requests constantly in flight.

## Findings and acceptance limits

1. **Medium — shared-IP capacity conflict.** Account traffic is limited to 120 requests/minute/IP; login traffic to 10/15 minutes/IP. Multiple users behind the same network consume one bucket. The measured profile can therefore be rejected despite low response latency. The aggregate 5/10 RPS requirement has not specified a route mix or shared-IP distribution; it cannot be accepted unconditionally with these policies. Keep the current protection for the personal trial; settle the expected shared-IP usage and review any policy change during step 5 rather than silently raising limits.
2. **Operational limitation — process-local counters.** Multi-instance hosting requires consistent rate/concurrency enforcement. Reverse-proxy trust and HTTPS/cookies need verification in the actual deployment; the test app deliberately uses loopback HTTP.
3. **Operational evidence pending.** Thirty-day redacted logging/retention, monthly availability and frontend web-vital targets have no production evidence here. Long-duration operation and distributed abuse were not tested.
4. **Medium — login latency target missed.** Ten accepted concurrent Argon2id logins reached p95 1,018.73 ms on this machine. Review resource capacity and bounded authentication scheduling in step 5; do not reduce password hashing protection merely to meet latency.

No new concrete High/Critical vulnerability was identified in the reviewed scope. This is not independent whole-system approval. The shared-IP finding and untested deployment controls remain visible acceptance gaps.
